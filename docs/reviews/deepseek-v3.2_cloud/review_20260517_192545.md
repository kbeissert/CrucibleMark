# CrucibleMark Review: deepseek-v3.2:cloud

> **Erstellt am:** 17.05.2026, 19:25:45


> **Kategorie:** General, Coder

deepseek-v3.2:cloud erreicht einen Gesamtscore von 73.26% und trägt im Leaderboard den Badge **"Unusable Cultural Expert"** — eine Kombination, die bereits alles über dieses Modell sagt, bevor man eine einzige Zeile der Protokolle liest: kulturelle Kompetenz vorhanden, Verlässlichkeit im Einsatz fragwürdig. Das Modell ist technisch solide aufgestellt, wird aber durch katastrophale Stabilitätswerte und einen folgenreichen Sprachfehler im Content-Modul weit unter seinem eigentlichen Potenzial bewertet. Sovereign Risk: HIGH — deepseek-v3.2:cloud wird über DeepSeeks eigene API auf Servern in China verarbeitet und unterliegt chinesischem Recht (PIPL, CSL, DSL), das staatlichen Behörden weitreichende Datenzugriffsrechte einräumt; ein DSGVO-konformes DPA existiert nicht.

Die Stabilitätslage ist das dominierende Thema dieses Reviews und muss vor jeder inhaltlichen Bewertung klar benannt werden. 26 von 43 Tests endeten mit einem Timeout. Das ist keine Häufung unglücklicher Netzwerkmomente, sondern ein systematisches Signal: Der DeepSeek-Cloud-Endpunkt ist zum Testzeitpunkt unter Last nicht verlässlich erreichbar. Da deepseek-v3.2:cloud als Cloud-Modell der Frontier-Klasse läuft, scheidet ein VRAM-Ceiling des Testsystems als Ursache aus — das Problem liegt beim Provider. Wer dieses Modell in eine Agenten-Pipeline oder einen produktiven Workflow einbaut, plant Ausfälle aktiv mit ein. Das Badge "Unusable" im Speed-Profil ist damit nicht nur eine Geschwindigkeitsaussage, sondern ein Verfügbarkeitsurteil.

Die Generierungsgeschwindigkeit von 2,91 Tokens/s ist, gemessen an anderen Frontier-Modellen im Leaderboard, das langsamste Ergebnis im gesamten Feld. Zum Vergleich: grok-4-fast erzielt 151,96 t/s, mistral-small 114,15 t/s. Selbst deutlich kleinere lokale Modelle liegen hier mehrfach schneller. Für den Kontext: Das Testsystem ist ein Apple Silicon M4 mit 24 GB Unified Memory — deepseek-v3.2:cloud läuft jedoch nicht lokal, sondern über die Cloud-API. Die 2,91 t/s sind also kein Hardware-Ceiling, sondern Ausdruck der Endpunkt-Performance unter den Testbedingungen. Wer mit dieser Geschwindigkeit ein Video-Script oder eine Sicherheitsanalyse generieren will, plant besser eine Kaffeepause ein.

## Code-Qualität und Security-Analyse

Das Code-Quality-Modul zeigt deepseek-v3.2:cloud von seiner technisch kompetenten Seite, auch wenn die Ergebnisse nicht uneingeschränkt überzeugen. Im Test `code_quality_002` analysierte das Modell einen sicherheitskritischen PHP-Code-Block und identifizierte 20 Schwachstellen in korrektem Tabellenformat mit allen geforderten Spalten (Vulnerability, Typ, Schweregrad, Warum unsicher, Fix). Die Abdeckung ist beachtlich: SQL-Injection-Varianten, Path Traversal, Session Fixation, CSRF, IDOR, Type Juggling und Mail Header Injection wurden alle erkannt und korrekt eingestuft. Der Hybrid-Score von 65,5% spiegelt jedoch einen strukturellen Mangel wider, der über die Tabelle hinausgeht.

Was fehlt, ist das, was einen Security-Audit von einer Vulnerability-Checkliste unterscheidet: narrative Synthese. Der Golden Standard liefert einen "Kritischen Angriffspfad", der zeigt, wie sich einzelne Schwachstellen zu einer vollständigen Systemkompromittierung ohne Authentifizierung verketten lassen. Das Modell liefert korrekte Einzelbefunde, aber keine Angriffskette. Es fehlt die Aussage, dass mindestens sieben der identifizierten Lücken eine vollständige Kompromittierung ohne vorherige Authentifizierung ermöglichen — ein Befund, der für jede produktive Einschätzung des Codes unverzichtbar wäre. Auch die IDOR-Fehlklassifikation als "Sekundäre SQL Injection" zeigt, dass das Modell Symptome erkennt, aber die eigentliche Schwachstellenkategorie gelegentlich verfehlt.

Das Modul ist mit einer Timeout-Rate von 5/5 im Test vollständig ausgefallen — sämtliche Code-Quality-Tests endeten im Timeout. Dass überhaupt ein verwertbares Protokoll vorliegt, ist einem der wenigen Tests zu verdanken, der noch eine Antwort produzierte. Für den Produktiveinsatz in Security-Workflows ist das ein Ausschlusskriterium.

## Logisches Reasoning

Im Reasoning-Modul zeigt das Modell solide Grundkompetenz. Der klassische Wächter-Rätsel-Test (`reasoning_metacog_003`) wurde mit einem Hybrid-Score von 82,5% bewertet. Das Modell kommt zur korrekten Lösung — "Wenn ich den anderen Wächter fragen würde, welche Tür zur Freiheit führt, was würde er sagen?" — und erklärt den Mechanismus der Doppelverneinung in verständlichem Deutsch. Die Verwendung der geforderten `<thought>`-Tags erfolgte korrekt und ohne Verweigerung, was für die Instruktions-Compliance spricht.

Die Lücke zum Golden Standard ist real, aber nicht dramatisch: Eine tabellarische Gegenüberstellung beider Fälle fehlt, die alternative Frageformulierung wird als "weniger sicher" abgetan statt erklärt, und die explizite Betonung der Universalität der Lösung ("Man muss nicht wissen, wer der Lügner ist") bleibt aus. Das sind Präsentationsfragen, keine Denkfehler. Der Judge bewertet das Ergebnis als "gut, aber nicht exzellent" — eine faire Einschätzung.

Die Timeout-Rate im Reasoning-Modul liegt bei 3/5, was die inhaltliche Bewertung unter Vorbehalt stellt: Was das Modell liefert, wenn es antwortet, ist brauchbar. Ob es antwortet, ist die eigentliche Frage.

## Cultural Intelligence

Das Cultural-Intelligence-Modul ist das Gegenmodell zu allem Gesagten: stabil, vollständig und qualitativ ansprechend. Mit einer Timeout-Rate von 0/5 und einem P95-Wert von 57,82 Sekunden lief dieses Modul absolut zuverlässig. Der Gesamtscore von 81,3 im Leaderboard ist das höchste Einzelmodul-Ergebnis des Modells und erklärt, warum der Badge "Cultural Expert" trotz allem vergeben wurde.

Im Test `cultural_intel_002` überarbeitete das Modell eine problematische Stellenanzeige korrekt auf Deutsch, entfernte toxische Sprache ("Ninja", "kill the competition", "manly courage") und ersetzte sie durch professionelle Formulierungen. Die Sprachvorgabe wurde eingehalten, die Struktur ist klar. Der Judge identifiziert zwei messbare Lücken: "Fachprofi" statt des geschlechtsneutraleren "Fachkraft" und ein fehlendes Call-to-Action-Element, das im deutschen Stellenanzeigenkontext Standard ist. Der Ton ist korrekt, aber etwas distanziert — wo der Golden Standard mit "freuen wir uns auf Ihre Bewerbung" psychologische Sicherheit schafft, bleibt das Modell bei "Wir schätzen" und "Wir legen Wert auf". Kompetent, aber ohne das letzte Quäntchen Wärme.

Der Modul-Score von 81,3 ist das einzige Ergebnis in diesem Review, das uneingeschränkt als Stärke bezeichnet werden kann.

## Content Transformation und der folgenreiche Sprachfehler

Das Content-Transformation-Modul offenbart einen der gravierendsten Einzelfehler im gesamten Benchmark. In `content_transformation_004` produzierte das Modell ein Video-Script in **Englisch**, obwohl die Aufgabe explizit auf Deutsch gestellt war. Der Judge stellt fest: DE=22, EN=132 Sprachmarker — das ist kein versehentliches Code-Switching, das ist eine vollständige Sprachverweigerung im Kerndokument.

In `content_transformation_004` überschritt das Modell zusätzlich das explizite Wortlimit von 900 Wörtern mit 1.102 detektierten Wörtern (122% des Limits). Das Scoring-System verhängte einen automatischen Abzug von 17,20 Punkten. Die inhaltliche Qualität der Antwort ist damit irrelevant — die Strafe greift regelbasiert und unabhängig davon, wie gut das Script strukturell war. Beide Violations treffen denselben Task, was das Bild verschärft: Unter simultanen Constraints aus Sprache, Länge und Format verlor das Modell sowohl die Sprachvorgabe als auch das Wortlimit als erste Bedingungen.

Das ist kein isolierter Ausreißer im Sinne eines Einzelfalls, sondern ein strukturelles Signal für ein bekanntes Muster: Wenn mehrere Constraints gleichzeitig aktiv sind, priorisiert das Modell inhaltliche Vollständigkeit über Formal-Compliance. Der Hybrid-Score von 54,4% für diesen Test ist die direkte Konsequenz. Interessanterweise bewertet der Judge den inhaltlichen Teil des Scripts — Ton, Pacing, Produktionsanweisungen — als qualitativ hochwertig. Das macht den Sprachfehler umso ärgerlicher: Das Modell konnte die Aufgabe, hat sie aber in der falschen Sprache gelöst.

## Datenschutz und Datenhoheit

deepseek-v3.2:cloud wird über DeepSeeks eigene API betrieben. Der Provider ist die Hangzhou DeepSeek Artificial Intelligence Co., Ltd. mit Sitz in China. Anwendbares Recht ist chinesisches Recht (PIPL, CSL, DSL), der Datenstandort liegt in China.

Das berechnete Sovereign Risk ist **HIGH**. DeepSeek unterliegt dem chinesischen National Security Law (NSL), das staatlichen Behörden unter bestimmten Voraussetzungen weitreichende Zugriffsrechte auf Daten und Modelle einräumt. Das Bundesamt für Sicherheit in der Informationstechnik (BSI) hat am 4. Februar 2025 explizit vor dem Einsatz des DeepSeek-Cloud-Dienstes gewarnt. Ein DSGVO-konformes Data Processing Agreement (DPA) ist nicht verfügbar, was für europäische Unternehmen, die personenbezogene Daten verarbeiten, ein konkretes Compliance-Hindernis darstellt. Die Datenspeicherungsdauer ist nicht dokumentiert.

Für Unternehmenseinsatz in der EU gilt: Wer deepseek-v3.2:cloud über die offizielle API nutzt, transferiert Anfragen auf Server in China und kann keine DSGVO-konforme Verarbeitungsgrundlage nachweisen. Das ist kein theoretisches Risiko, sondern ein praktisches Deployment-Hindernis. Die Open-Weights-Variante des Modells kann lokal betrieben werden, was das cloud-spezifische Datentransfer-Risiko eliminiert — das Weights-Provenienz-Risiko (chinesische Herkunft, NSL-Exposition) bleibt jedoch als Bewertungsfaktor bestehen.

## Fazit

deepseek-v3.2:cloud ist ein Modell mit echten Stärken, das im Cloud-Betrieb an seinen eigenen Endpunkten scheitert. Ein Gesamtscore von 73,26% klingt respektabel — und wäre es auch, wenn 60% der Tests nicht im Timeout geendet hätten. Die inhaltliche Qualität, wo sie messbar ist, zeigt ein Modell mit solider Code-Kompetenz, brauchbarem Reasoning und überraschend gutem kulturellen Feingefühl. Halluzinationen sind in den vorliegenden Protokollen kein Thema — das Modell erfindet lieber nichts, als sich zu blamieren.

Das Problem ist struktureller Natur. 26 Timeouts bei 43 Tests, eine P95-Latenz von 527 Sekunden und 2,91 t/s Generierungsgeschwindigkeit sind keine Ausreißer, sondern Charaktermerkmale des Endpunkts unter den Testbedingungen. Der Speed-Badge "Unusable Cultural Expert" trifft den Kern: Das Modell kann etwas, ist aber in dieser Konfiguration nicht verlässlich einsetzbar.

Für Teams, die die Open-Weights-Variante lokal oder über stabilere Inference-Provider betreiben, sieht die Rechnung anders aus. Wer deepseek-v3.2:cloud über DeepSeeks eigene API nutzt, sollte Retry-Logik, Timeouts und einen Fallback-Provider als Pflichtbestandteil der Integration betrachten — und die Datenschutzlage vorab mit der Rechtsabteilung klären.
