## Performance und Geschwindigkeit

Wer qwen3:14b auf dem Testsystem betreibt, bekommt kein Werkzeug für interaktive Dialoge, sondern einen geduldigen Analysten, der in der Nacht arbeitet. Der Badge ist dabei ehrlich gemeint: Batch-Verarbeitung von Code-Reviews, Dokumentationsgenerierung oder Content-Transformation sind die natürlichen Lebensräume dieses Modells. Für Echtzeit-Anwendungen — Autocomplete, interaktive Agenten, synchrone API-Calls — ist die Geschwindigkeit eine strukturelle Absage.

Die P95-Antwortzeit von 116.62 Sekunden unterstreicht das. Das ist kein Ausreißer-Problem, das man mit Retry-Logik löst; es ist ein Architektur-Profil. Das Modell denkt, auch wenn der Thinking-Modus nicht explizit aktiviert ist. Als Thinking-Optional-Architektur (qwen3:14b unterstützt Extended Thinking per API, dieser Modus war im Benchmark nicht aktiviert) kann das Modell auch im Standard-Betrieb mehr interne Verarbeitungsschritte durchführen als reine Instruction-Modelle — was die Latenz nach oben treibt. Auf dem Testsystem mit Apple Silicon M4 und 24 GB Unified Memory läuft das 14B-Modell vollständig im RAM ohne Swapping-Risiko; die Geschwindigkeitsbremse sitzt nicht in der Hardware, sondern in der Modellarchitektur selbst.

## Code Quality und Security Audit

66.8 Punkte im Code-Quality-Modul — auf dem Papier ein solides Ergebnis für ein 14B-Desktop-Modell. Die Protokolle erzählen eine differenziertere Geschichte.

Im Security-Audit (code_quality_002) identifiziert qwen3:14b 14 von 19 Schwachstellen, was einer Erkennungsrate von etwa 74 Prozent entspricht. Die Lücken sind nicht trivial: Hardcoded DB-Credentials ohne Passwort, fehlende CSRF-Protection, eine Header-Injection nach dem Login-Redirect und Session Fixation fehlen vollständig. Noch schwerwiegender ist die Fehleinschätzung bei den erkannten Schwachstellen: Type Juggling mit `==` in Authentifizierungskontexten wird als Medium eingestuft, obwohl es ein kritisches Authentication-Bypass-Risiko darstellt. Path Traversal landet bei High statt Critical. Der Admin-Cookie-Check, der eine vollständige client-seitige Authentifizierung darstellt, wird ebenfalls unterschätzt.

Der Judge formuliert es präzise: "~50% der Severity-Klassifikationen sind gegenüber dem Golden Standard herabgestuft." Das ist keine Kleinigkeit in einem Security-Kontext. Wer qwen3:14b für automatisierte Code-Reviews einsetzt, bekommt eine nützliche erste Durchsicht — aber kein Instrument, dem man kritische Sicherheitsentscheidungen anvertrauen sollte, ohne die Ergebnisse manuell zu validieren.

Die Formatierung ist korrekt: saubere Markdown-Tabelle, deutsche Ausgabe, keine technischen Fehler. Das Modell weiß, wie man eine Tabelle baut. Es weiß nur nicht immer, was in die Severity-Spalte gehört.

Empfehlenswert für: Batch-Dokumentationsaufgaben, erste Code-Review-Durchgänge als Vorfilter, Content-Transformation-Workflows ohne Sprachkritikalität. Nicht empfehlenswert für: Security-Audits als Abschlussbewertung, interaktive Agenten-Frameworks, mehrsprachige Deployments ohne Output-Validierung. Wer das Modell lokal betreibt, hat die Datenschutz-Frage elegant gelöst; wer es über API einsetzt, sollte die Sovereign-Risk-Einstufung nicht als abstrakte Warnung lesen.
