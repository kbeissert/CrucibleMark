# CrucibleMark Review: gemma4:26b

> **Erstellt am:** 11.04.2026, 16:46:54


> **Kategorie:** General

Googles gemma4:26b erreicht einen Gesamtscore von 65.07% und trägt den Speed-Badge "Batch DevOps Expert" — eine Klassifizierung, die ehrlicher kaum sein könnte. Das Modell denkt gründlich, braucht dafür aber Zeit, und liefert in technischen Kerndisziplinen Ergebnisse, die für ein lokales 26-Milliarden-Parameter-Modell respektabel sind. Wo es scheitert, scheitert es konsistent: Sobald Sprachvorgaben und Formatanforderungen gleichzeitig unter Druck geraten, verliert das Modell die Kontrolle über seine eigene Ausgabe. Die Weights stammen von Google DeepMind und sind öffentlich verfügbar; bei rein lokaler Nutzung ohne API-Anbindung entfällt das CLOUD-Act-Risiko vollständig.

## Performance und Geschwindigkeit

Mit 12.98 Tokens pro Sekunde ist gemma4:26b ein Geduldsspiel für alle, die schnelle Interaktion erwarten. Der Badge "Batch DevOps Expert" trifft es präzise: Das Modell ist für asynchrone Workflows gebaut, nicht für den Dialog. Wer Anfragen sequenziell abarbeitet und auf Ergebnisse warten kann, bekommt brauchbare Qualität. Wer im Terminal auf eine Antwort starrt, wird ungeduldig.

Auf dem Referenzsystem — Apple Silicon M4, 24 GB Unified Memory (Shared RAM/VRAM) — läuft das Modell ohne Swapping-Probleme, aber der P95-Wert zeigt, dass komplexe Reasoning-Aufgaben die Grenzen des verfügbaren Speichers spürbar belasten. Bei 26 Milliarden Parametern in quantisierter Form ist das erwartbar; wer ein flüssigeres Erlebnis sucht, muss entweder Hardware nachrüsten oder auf die Cloud-Variante (gemma4:31b-cloud) ausweichen, die im Leaderboard mit 40.24 t/s deutlich komfortabler liegt.

## Token-Effizienz

Das Modell verhält sich in den meisten Modulen erfreulich token-ökonomisch. Code Quality, Documentation Quality, Content Transformation und UX Writing liegen alle unter dem Fleet-Median — das ist für ein lokales Modell ein echter Vorteil, weil weniger Output direkt in kürzerer Latenz resultiert.

Eine Ausnahme fällt auf: Im Cultural-Intelligence-Modul produziert gemma4:26b durchschnittlich 640 Tokens bei einem Fleet-Median von 238 — ein Faktor von 2.69. Das Modell schreibt dort fast dreimal so viel wie der Durchschnitt der getesteten Modelle. Da Cultural Intelligence gleichzeitig das schwächste Modul des Modells ist (dazu gleich mehr), ist das keine Stärke, sondern ein doppeltes Problem: viel Text, wenig Qualität.

## Code Quality und Security

Mit 74.9 Punkten im Code-Quality-Audit zeigt gemma4:26b seine deutlichste Stärke. Das Modell identifiziert in einem PHP-Sicherheitsaudit 14 von 19 Schwachstellen korrekt — eine Abdeckung von rund 74 Prozent, die für ein lokales Modell dieser Größe ordentlich ist. SQL Injection in Login, Reset und Delete-Pfaden, Plaintext-Passwörter, Broken Access Control über Cookie-basierte Admin-Prüfung, CSRF, Session Fixation, Path Traversal: alles erkannt, korrekt klassifiziert, mit funktionalen Fixes versehen.

Wo das Modell ins Straucheln gerät, ist die Tiefe. Fünf Schwachstellen fehlen vollständig: hardcodierte API-Secrets, hardcodierte Datenbankzugangsdaten mit Root-Rechten ohne Passwort, Header Injection nach Output, Reset-Token ohne Ablaufzeit. Und bei Type Juggling — einer der kritischsten PHP-Fallen, weil `true == "s8sk_api_2024"` tatsächlich `true` ergibt — stuft das Modell die Schwere als "Medium" ein, obwohl ein vollständiger Authentication-Bypass vorliegt. Das ist kein Randproblem: Wer diesen Fehler in einem echten Audit übersieht oder kleinredet, liefert dem Auftraggeber ein falsches Sicherheitsgefühl.

Die Fixes selbst sind korrekt, aber schematisch. `password_hash()`, `htmlspecialchars()`, `basename()` — alles richtig, alles ohne Kontext. Warum `hash_equals()` für timing-sichere Vergleiche besser ist als direkter String-Vergleich, warum API-Secrets in Umgebungsvariablen gehören und nicht im Quellcode, warum ein dedizierter Datenbanknutzer mit minimalen Rechten die Schadensbegrenzung im Kompromittierungsfall erheblich verbessert: Das bleibt unerwähnt. Für einen Entwickler, der den Code selbst schreibt und nur einen zweiten Blick braucht, reicht das. Für eine vollständige Sicherheitsprüfung ist es zu dünn.

## Logik und Reasoning

Im Logical-Reasoning-Modul erzielt gemma4:26b 68.68 Punkte — ein solides Ergebnis, das zeigt, dass das Modell strukturierte Denkaufgaben grundsätzlich beherrscht. Am klassischen Zwei-Wächter-Rätsel demonstriert es das korrekt: Die Kernantwort ("Was würde der andere Wächter sagen, wenn ich ihn nach dem Freiheitstor frage?") ist präzise, die Mechanik des doppelten Negationseffekts wird sauber durchgespielt, beide Szenarien (Wahrheitssager und Lügner) werden explizit durchgerechnet.

Was fehlt, ist die zweite Ebene. Das Modell löst das Rätsel, aber es erkundet es nicht. Alternative Formulierungen der Frage, die Frage nach der Robustheit der Lösung gegen Variationen des Rätsels, die Einordnung als Technik selbstreferenzieller Fragen — das alles bleibt aus. Für eine als "General" eingestufte Architektur ist das kein Versagen, aber es markiert die Grenze zwischen einem Modell, das Aufgaben löst, und einem, das Probleme durchdenkt.

Der eine Timeout im Reasoning-Modul bei einem P95 von 176 Sekunden ist ein konkretes Warnsignal für Agenten-Frameworks: Wer gemma4:26b in eine Pipeline einbaut, die auf Antworten wartet, muss großzügige Timeout-Schwellen und Retry-Logik einplanen.

## UX Writing und Content Transformation

Im UX-Writing-Modul (61.15 Punkte) und Content Transformation (73.57 Punkte) zeigt das Modell ein gespaltenes Bild. Die inhaltliche Qualität ist oft gut — wenn das Modell die Aufgabe versteht und die Sprachvorgabe einhält. Aber genau da liegt das strukturelle Problem.

Das Sprachversagen ist kein isolierter Ausreißer. Über mindestens zwei Tests des Content-Transformation-Moduls zeigt gemma4:26b ein konsistentes Muster: Bei simultanen Constraints aus Sprache, Länge und Format verliert es die Sprachvorgabe als erste Bedingung. In `content_transformation_004.md` ist das Kernproblem eindeutig: Der gesamte Video-Script-Körper wird auf Englisch produziert, obwohl die Aufgabe explizit auf Deutsch gestellt ist und eine deutsche Ausgabe verlangt. Die Analyse-Sektion ist korrekt auf Deutsch, das eigentliche Deliverable nicht. Dasselbe Muster taucht im Cultural-Intelligence-Modul auf, wo 80 Prozent der Antwort auf Englisch verfasst sind, obwohl die Aufgabe eine ausschließlich deutsche Ausgabe fordert. In beiden Fällen bewertet der Judge die inhaltliche Qualität der tatsächlich produzierten Texte als gut bis sehr gut — der Score-Schaden entsteht nicht aus Denkfehlern, sondern aus der Weigerung, die Sprachvorgabe zu respektieren.

Zusätzlich überschreitet das Modell in `content_transformation_004.md` das explizite Wortlimit von 600 Wörtern mit 767 produzierten Wörtern (128 Prozent des Limits), was eine automatische 20-Prozent-Punktabzug auslöst. Sprachversagen und Längenproblem treten hier kombiniert auf — das ist kein Zufall, sondern ein Zeichen dafür, dass das Modell unter hohem Constraint-Druck die Kontrolle über seine Ausgabeparameter verliert.

Für den Produktiveinsatz bedeutet das: Jede Aufgabe, die gleichzeitig Sprache, Länge und Format vorschreibt, muss mit expliziten Nachkontroll-Schritten abgesichert werden. Das Modell liefert keine zuverlässige Zero-Shot-Compliance unter kombinierten Bedingungen.

Dass der Judge die tatsächliche deutsche Textqualität mit 4/5 bewertet, macht den Gesamtscore von 10/100 in diesem Test umso bitterer — die Kompetenz ist vorhanden, die Instruction-Following-Zuverlässigkeit nicht.

## Datenschutz und Datenhoheit

Die Weights von gemma4:26b stammen von Google DeepMind, einem US-amerikanischen Unternehmen, das dem CLOUD Act unterliegt. Für die rein lokale Nutzung — wie in diesem Benchmark — ist das unmittelbar irrelevant: Wer die Weights lokal betreibt und keine API-Anfragen an Google sendet, hat keinen Datentransfer und damit kein CLOUD-Act-Exposure. Das berechnete Sovereign Risk ist entsprechend als MEDIUM eingestuft, primär weil die Weights-Provenienz aus dem US-amerikanischen Rechtsraum stammt, die lokale Betreibbarkeit aber das Risiko strukturell begrenzt.

Für Unternehmen, die auf die Google-API-Variante zurückgreifen, gilt: Google LLC verarbeitet Daten in den USA, ein GDPR DPA ist verfügbar, die Datenspeicherdauer beträgt 30 Tage. SCCs und DPA sind vorhanden, was die formale DSGVO-Compliance-Basis für EU-Kunden schafft. Der CLOUD Act bleibt dennoch geltendes US-Recht: US-Behörden können unter bestimmten Voraussetzungen Zugriff auf verarbeitete Daten verlangen, auch wenn Google europäische Standardvertragsklauseln anbietet. Wer sensible Unternehmensdaten verarbeitet, sollte die lokale Deployment-Option der API-Nutzung vorziehen.

## Fazit

gemma4:26b ist ein technisch kompetentes Modell mit einem klaren Profil: Es ist ein Batch-Werkzeug für DevOps-nahe Aufgaben, kein Gesprächspartner für interaktive Workflows. Die Code-Quality-Ergebnisse (74.9 Punkte) und die Reasoning-Performance (68.68 Punkte) zeigen, dass das Modell in seinem Kernbereich liefert — mit den beschriebenen Einschränkungen bei Tiefe und Vollständigkeit. Über alle Tests hinweg keine nennenswerten Halluzinationen; das Modell erfindet lieber nichts, als sich zu blamieren.

Das strukturelle Problem ist die Instruction-Following-Zuverlässigkeit unter kombinierten Constraints. Wer das Modell in Pipelines einsetzt, die gleichzeitig Sprache, Format und Länge vorschreiben, wird ohne Nachkontrolle regelmäßig fehlerhafte Ausgaben erhalten. Das ist kein gelegentlicher Ausreißer, sondern ein reproduzierbares Muster. Mit 12.98 t/s und einem P95 von 80 Sekunden ist das Modell außerdem klar für asynchrone Batch-Verarbeitung positioniert — wer Echtzeit-Interaktion erwartet, wird enttäuscht.

Empfehlenswert für: Entwickler, die lokale Inferenz ohne Cloud-Abhängigkeit benötigen, Batch-Pipelines für Code-Review und Security-Audits, Umgebungen mit 24 GB Unified Memory, die kein Swapping riskieren wollen. Nicht empfehlenswert für: mehrsprachige Content-Pipelines mit strikten Sprachvorgaben, interaktive Anwendungen mit Latenz-Anforderungen, vollständige Sicherheitsaudits ohne menschliche Nachkontrolle.
