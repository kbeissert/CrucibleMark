Was fehlt, ist Tiefe: Der Golden Standard liefert eine explizite Case-by-Case-Verifikation, ein Tabellenformat und alternative Formulierungsansätze. Das Reasoning-Modul produziert im Schnitt 839 Tokens, was unter dem Fleet-Median von 972 Tokens liegt. Für ein Instruct-Modell, das auf kompakte Antworten trainiert ist, ist das konsistent — die Architektur-Kategorie erklärt dieses Verhalten. Wer tiefere Chain-of-Thought-Ausführungen braucht, ist bei einem Thinking-Modell besser aufgehoben.

Das Sprachproblem im Reasoning-Modul ist allerdings gravierend und kein Einzelfall. Unter simultanen Constraints aus Sprache, Aufgabenformat und Reasoning-Tiefe verliert das Modell die Sprachvorgabe als erste Bedingung — über vier Tests hinweg konsistent. Der Score-Abzug ist methodisch korrekt: CrucibleMark bewertet Instruction-Compliance als reales Alltagsmerkmal, und ein Modell, das im Produktiveinsatz ohne Nachkontrolle die falsche Sprache liefert, ist ein konkretes Deployment-Risiko.

## Code Quality und Security: Solide Basis, kritische Lücken

Mit 69.2 Punkten im Code-Quality-Modul liegt gemma3:12b unter dem Niveau, das man von einem Allrounder dieser Größe erwarten würde. Das Security-Audit in `code_quality_002` illustriert das Problem präzise: Das Modell identifiziert 15 Schwachstellen in tabellarischer Form, der Golden Standard nennt 19 — aber die Differenz ist weniger das eigentliche Problem als die Qualität der Einordnung.

Vier kritische Schwachstellen werden vom Modell systematisch falsch bewertet. Die SQL-Injection im DELETE-Statement erhält "Standard/Medium" statt "Critical", obwohl `id=$uid` ohne Quotes triviale Integer-basierte Injections ermöglicht. Path Traversal wird ebenfalls als "Standard/High" eingestuft, obwohl der `strpos`-Check mit `../config.php` oder einem einfachen Path-Traversal-Payload umgehbar ist — was den Status "Critical" rechtfertigt. Type Juggling beim API-Key-Vergleich (`true == "s8sk_api_2024"` ergibt in PHP `true`) und die Cookie-basierte Authentifizierung als vollständiger Authorization-Bypass erhalten beide zu niedrige Severity-Ratings. Für einen Security-Audit ist das keine Kleinigkeit: Wer auf Basis dieser Bewertung priorisiert, behandelt kritische Lücken als mittelschwere Probleme.

Darüber hinaus fehlen im Modell-Output vollständig: Hardcoded DB-Credentials ohne Passwort, fehlende CSRF-Protection, Reset-Token ohne Ablaufzeit, Header-Injection nach Output und unsichere Auth-Cookie-Flags. Besonders schwerwiegend ist das Fehlen von Proof-of-Concept-Angriffsketten, die der Golden Standard explizit liefert. Ein Security-Professional, der dieses Audit als Grundlage nutzt, hätte ein unvollständiges Risikobild.

Der Judge fasst es nüchtern zusammen: "A security professional using this audit would miss critical vulnerabilities and misunderstand the true risk profile of the application." Das ist ein harter Befund, aber ein fairer.

## Datenschutz und Datenhoheit

gemma3:12b stammt von Google DeepMind, einem US-amerikanischen Unternehmen mit Sitz in Mountain View, Kalifornien. Das berechnete Sovereign Risk ist MEDIUM. Die Begründung ist differenziert: Wer die Open Weights lokal betreibt, überträgt keine Daten an Google-Server, und der CLOUD Act greift primär bei API- und Cloud-Nutzung. Die Weights-Provenienz selbst trägt das Medium-Rating, weil Google DeepMind als US-Unternehmen grundsätzlich dem CLOUD Act unterliegt — auch wenn dieser Aspekt bei rein lokalem Deployment keine operative Relevanz entfaltet.

Für Nutzer, die das Modell über Googles API oder Cloud-Infrastruktur betreiben, sieht die Lage anders aus: Datenstandort ist die USA, Datenspeicherung erfolgt für bis zu 30 Tage, und ein GDPR Data Processing Agreement ist verfügbar. EU-Unternehmen können damit formal eine DSGVO-konforme Verarbeitungsgrundlage schaffen, müssen aber die CLOUD-Act-Implikation einkalkulieren: US-Behörden können unter bestimmten Voraussetzungen Zugriff auf verarbeitete Daten verlangen, auch wenn Google SCCs anbietet. Für den lokalen Betrieb der Open Weights bleibt das eine theoretische Überlegung — praktisch relevant wird sie erst, wenn Daten die eigene Infrastruktur verlassen.

## Fazit

Die 19.76 Tokens pro Sekunde reichen für interaktive Nutzung, der P95-Wert von 61.82 Sekunden zeigt aber, dass Ausreißer im komplexen Aufgabenbereich spürbar werden.

Das strukturelle Problem ist das Sprachverhalten. Vier von fünf Reasoning-Metacognition-Tests und ein Content-Transformation-Test produzieren englische Ausgaben trotz expliziter Deutschvorgabe — das ist kein Ausreißer, das ist ein Muster. Für jeden Einsatz, bei dem Sprachkonsistenz ohne manuelle Nachkontrolle erwartet wird, ist das ein echtes Deployment-Risiko. Ergänzend dazu zeigt das Security-Audit-Modul Schwächen in der Severity-Einordnung kritischer Schwachstellen, die im Produktiveinsatz direkt zu falschen Priorisierungen führen könnten.

Über alle Tests hinweg keine nennenswerten Halluzinationen — das Modell erfindet lieber nichts, als sich zu blamieren.

Empfehlung: gemma3:12b ist eine solide Wahl für lokale Allrounder-Aufgaben, bei denen Deutsch-Compliance nicht kritisch ist oder manuell geprüft wird. Cultural Intelligence, generelles Reasoning und stabile Laufzeit auf Desktop-Hardware sind echte Pluspunkte. Für Security-Audits, mehrsprachige Produktiv-Pipelines oder tiefe Dokumentationsaufgaben braucht es entweder Prompt-Engineering-Absicherung oder ein stärkeres Modell. Die Weights stammen von Google DeepMind und sind bei lokalem Betrieb ohne Cloud-Abhängigkeit nutzbar — wer Datensouveränität priorisiert, findet hier eine der wenigen Optionen, die das ohne Abstriche ermöglicht.
