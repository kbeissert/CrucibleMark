## Geschwindigkeit und Infrastruktur

Mit 7,9 Tokens pro Sekunde bewegt sich qwen3.5:9b am unteren Ende der lokalen Edge-Modelle im Testfeld. Der Badge "Batch DevOps Expert" beschreibt das korrekt: Dieses Modell ist kein Werkzeug für interaktive Dialoge oder reaktive Agenten-Pipelines. Die 14 Timeouts und die P95-Zeit von 224 Sekunden sind keine Netzwerkprobleme, sondern ein klares Indiz dafür, dass das Modell trotz seiner nominellen 9-Milliarden-Parameter-Klasse (Edge-Tier, 5–9B) auf diesem Setup an Kapazitätsgrenzen stößt. Wer qwen3.5:9b produktiv einsetzen will, sollte das auf dedizierter Hardware mit ausreichend reserviertem VRAM testen, bevor er Schlüsse aus den hier gemessenen Geschwindigkeitswerten zieht.

Als Thinking-Optional-Modell kann qwen3.5:9b Extended Thinking per API aktivieren — dieser Modus war im Benchmark nicht eingeschaltet. CrucibleMark misst das Out-of-the-Box-Verhalten ohne explizites Thinking-Budget, was dem typischen API-Einsatz ohne Sonderkonfiguration entspricht. Dass das Modell auch im Standard-Modus intern mehr Verarbeitungsschritte durchführt als reine Instruction-Modelle, erklärt einen Teil der Latenz — aber nicht 14 Timeouts.

## Code Quality und Security

Die Code-Quality-Ergebnisse sind das stärkste Argument für qwen3.5:9b — mit einem Score von 67,2% liegt das Modell in diesem Modul spürbar über seinem Gesamtniveau. Das Protokoll aus `code_quality_002` zeigt, warum: Das Modell identifiziert 15 von 19 Sicherheitslücken korrekt, liefert die Ausgabe in sauberem deutschem Markdown, priorisiert nach Schweregrad und trifft die Formatanforderungen. SQL Injection, Session Fixation, Path Traversal, schwache Zufallsgenerierung, Type Juggling, Mail Header Injection, CSRF — das ist kein oberflächliches Scanning, sondern echte Sicherheitsanalyse.

Vier Lücken fehlen: IDOR (Insecure Direct Object Reference) in der Profilaktualisierung, Reflected XSS in der Welcome Message, Header Injection nach Output und fehlende Token-Ablaufzeiten beim Passwort-Reset. Das ist eine Vollständigkeitslücke von 21%, die bei einem Security-Audit im produktiven Einsatz schmerzhaft auffallen würde. Besonders das Übersehen von IDOR ist relevant, da es laut Golden Standard eine kritische Schwachstelle mit Privilege-Escalation-Potenzial darstellt. Die Severity-Einschätzung für Type Juggling (als "Standard" statt "Expert" klassifiziert) unterschätzt zudem einen PHP-spezifischen Angriffspfad, der in der Praxis unterschätzt wird.

Die Erklärungstiefe bleibt hinter dem Referenzstandard zurück: keine Attack-Chain-Kontexte, keine Proof-of-Concept-Beispiele, keine Begründung, warum bestimmte Fixes funktionieren. Für ein Modell, das im CLI-Bereich 86,12% erzielt und damit DevOps-Kommandos sauber beherrscht, ist das eine Lücke in der Vermittlungsqualität, nicht in der Detektionsfähigkeit.

Die Timeout-Rate von 2/5 im Code-Quality-Modul bedeutet, dass 40% der Tests nicht abgeschlossen wurden. Auch hier gilt: Was das Modell abliefert, ist brauchbar; was es nicht abliefert, ist das eigentliche Problem.

## Datenschutz und Datenhoheit

qwen3.5:9b ist ein Open-Weights-Modell von Alibaba Cloud, das lokal betrieben werden kann. Die Weights-Provenienz ist dabei der zentrale Datenschutzaspekt: Alibaba Cloud unterliegt als chinesisches Unternehmen dem National Security Law (NSL), dem Cybersecurity Law (CSL), dem Data Security Law (DSL) und dem Personal Information Protection Law (PIPL). Diese Gesetze räumen chinesischen Behörden weitreichende Datenzugriffsrechte ein — auch auf Modellentwicklungsprozesse.

Das berechnete Sovereign Risk ist HIGH. Für den lokalen Betrieb bedeutet das: Inferenz-Daten verlassen das eigene System nicht, solange keine Cloud-API von Alibaba genutzt wird. Wer die Weights lokal betreibt, ist von direkten API-Datenzugriffen abgeschirmt. Die Frage, welche Trainingsdaten in das Modell eingeflossen sind und ob diese unter chinesischem Recht erhoben wurden, bleibt jedoch offen und ist für sicherheitssensible Einsatzbereiche relevant.

Für europäische Unternehmen, die qwen3.5:9b über die Alibaba-Cloud-API nutzen würden: API-Anfragen unterliegen chinesischem Recht. Ein GDPR DPA ist laut Provider Card verfügbar, Standard Contractual Clauses (SCCs) sind vorhanden — bieten aber keinen gleichwertigen Schutz wie ein EU-Angemessenheitsbeschluss. Für DSGVO-kritische Workloads ist lokaler Betrieb der einzige vertretbare Ansatz.

## Fazit

qwen3.5:9b ist ein Modell mit echten Stärken in einem engen Korridor: Security-Analyse, CLI-Kommandos und grundlegendes Reasoning funktionieren besser als der Gesamtscore vermuten lässt. Wer es auf geeigneter Hardware betreibt und ausschließlich englischsprachige Aufgaben ohne strenge Längenvorgaben stellt, bekommt einen soliden Edge-Companion für Batch-Workloads.

Das Problem ist der Rest. Die Sprachkonsistenz-Schwäche ist keine Kleinigkeit: Über fünf dokumentierte Sprachmismatch-Violations in Cultural Intelligence und UX Writing hinweg ignoriert das Modell die Deutschvorgabe mit einer Regelmäßigkeit, die jeden mehrsprachigen Produktionseinsatz zur Lotterie macht. Die Hard-Constraint-Violations in Content Transformation und UX Writing — 719% beziehungsweise 536% über dem Wortlimit — sind keine Ausreißer, sondern Symptome desselben Grundproblems: Das Modell verliert unter simultanen Format-, Sprach- und Längenvorgaben die Kontrolle über seine eigene Ausgabe. Die Timeout-Rate von 14/43 macht das Bild vollständig.

Für den Einsatz empfehlenswert ist qwen3.5:9b als lokales Hilfswerkzeug für englischsprachige Security-Reviews, CLI-Skript-Generierung und einfache Reasoning-Aufgaben ohne strenge Formatbindung, auf Hardware, die mehr Headroom bietet als das hier verwendete Testsystem. Für Agenten-Frameworks, mehrsprachige Pipelines oder jeden Kontext, in dem Ausgabeformat und Zielsprache nicht verhandelbar sind, ist es zum jetzigen Zeitpunkt nicht einsetzbar. Über alle Tests hinweg keine nennenswerten Halluzinationen — das Modell erfindet lieber nichts, als sich zu blamieren, was in einem so unruhigen Profil wie diesem fast schon als Tugend durchgeht.
