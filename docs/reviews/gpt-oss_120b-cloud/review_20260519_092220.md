## Architektur und Geschwindigkeit

Die MoE-Architektur von gpt-oss:120b-cloud ist kein Marketingbegriff, sondern erklärt direkt das gemessene Verhalten: 56,29 Tokens pro Sekunde bei einem 120-Milliarden-Parameter-Modell sind ein Ergebnis, das Dense-Architekturen vergleichbarer Größe deutlich hinter sich lässt. Der Badge "Real-Time DevOps Expert" ist in diesem Kontext präzise vergeben — das Modell reagiert schnell genug für interaktive Terminal-Workflows, CLI-Pipelines und Agenten-Loops, in denen Latenz direkt als Reibungsverlust spürbar wird.

Hinzukommt, dass gpt-oss:120b-cloud zur Kategorie Thinking-Optional gehört: Extended Thinking lässt sich per API aktivieren und ermöglicht konfigurierbare Reasoning-Intensität über System-Prompts (low, medium, high). CrucibleMark testet alle Modelle im Standard-Modus ohne explizites Thinking-Budget, um vergleichbare Ausgangsbedingungen zu schaffen. Die hier gemessene Geschwindigkeit entspricht also dem Out-of-the-Box-Verhalten ohne aktiviertes Extended Thinking — ein Nutzer, der das Reasoning-Budget hochdreht, muss mit spürbar höherer Latenz rechnen, erhält dafür aber potenziell tiefere Analysen. Diese Architekturentscheidung ist eine Stärke, keine Einschränkung: Das Modell ist konfigurierbar, nicht festgelegt.

Die Klassifizierung als Frontier-Modell (Open Weights, Cloud-Deployment) bedeutet, dass die gemessene Geschwindigkeit nicht von lokaler Hardware abhängt. Die 56,29 t/s sind Cloud-seitig stabil reproduzierbar — kein Swapping-Risiko, kein VRAM-Ceiling. Wer das Modell lokal betreiben möchte, benötigt Server-Hardware; das Testsystem (Apple Silicon M4, 24 GB Unified Memory) wäre für ein 120B-Modell dieser Größenordnung im lokalen Betrieb schlicht ungeeignet.

## Code Quality und Security Audit

Mit einem Code-Quality-Score von 76,6% liefert gpt-oss:120b-cloud eine technisch solide Leistung. Im Security-Audit (code_quality_002) identifiziert das Modell exakt 19 Schwachstellen — deckungsgleich mit dem Golden Standard — und klassifiziert deren Schweregrade korrekt. SQL Injection, Path Traversal, Type Juggling, IDOR und Admin Cookie Bypass werden als Critical eingestuft; Plaintext Passwords, Mail Header Injection und Hardcoded Secrets als High. Die vorgeschlagenen Fixes sind technisch präzise: Prepared Statements für SQL Injection, `password_hash()` und `password_verify()` für Klartext-Passwörter, `hash_equals()` für Timing-sichere Vergleiche, `bin2hex(random_bytes(32))` für sichere Token. Das ist kein generisches Sicherheitswissen, sondern konkret anwendbarer Code-Rat.

Wo das Modell gegenüber dem Golden Standard zurückbleibt, ist die synthetisierende Ebene. Ein kritischer Angriffspfad, der zeigt, wie Schwachstellen in einer Kette eskalieren — SQL Injection zu Admin Cookie zu Delete All Users zu Path Traversal zu CSRF — fehlt vollständig. Ebenso fehlt eine Executive Summary, die den Gesamtrisikostatus des analysierten Codes auf den Punkt bringt. Der Judge fasst es treffend zusammen: Das Modell liefert eine starke Analyse einzelner Schwachstellen, aber keine Synthese ihrer kombinierten Wirkung. Für eine Sicherheitsprüfung, die in einem Ticketsystem landet, ist das ausreichend; für einen Audit-Report, der dem Management vorgelegt wird, fehlt die Rahmung.

Das Markdown-Tabellen-Format ist korrekt und sauber, alle Pflicht-Spalten (Vulnerability, Typ, Schweregrad, Warum unsicher, Fix) sind vorhanden. Die Formatierungsqualität ist tadellos.

Der Judge bestätigt: keine Logikfehler, vollständig korrektes Ergebnis auf Deutsch.

Der Score-Abzug entsteht nicht aus Denkfehlern, sondern aus Tiefenunterschieden gegenüber dem Golden Standard. Das Modell präsentiert einen einzigen Lösungsweg, wo der Standard alternative Frageformulierungen, eine tabellarische Fallübersicht, ein ASCII-Diagramm und eine konzeptuelle Einordnung in das Prinzip selbstreferenzieller Fragen bietet. Das ist kein Reasoning-Versagen, sondern ein Vollständigkeitsproblem: Das Modell denkt richtig, schreibt aber nicht alles auf, was es könnte.

Für einen Nutzer, der eine schnelle, korrekte Antwort braucht, ist das kein Problem. Für einen Einsatz, bei dem nachvollziehbare Denkpfade und Alternativbetrachtungen dokumentiert werden müssen, ist die Kürze ein realer Mangel.

## Datenschutz und Datenhoheit

gpt-oss:120b-cloud wird über OpenAI als Cloud-Provider bereitgestellt. Das berechnete Sovereign Risk ist MEDIUM: OpenAI, L.L.C. hat seinen Sitz in San Francisco, Kalifornien, und unterliegt dem US CLOUD Act. Das bedeutet konkret, dass US-Behörden unter bestimmten Voraussetzungen Zugriff auf bei OpenAI gespeicherte Daten verlangen können — auch wenn diese physisch außerhalb der USA liegen sollten. Das ist geltendes US-Recht, kein theoretisches Szenario.

Für EU-Unternehmen, die DSGVO-konform operieren müssen, ist die Lage differenziert: Ein GDPR Data Processing Agreement (DPA) ist verfügbar, OpenAI stellt Standardvertragsklauseln (SCCs) bereit, und die Datenspeicherungsdauer beträgt 30 Tage. Das beseitigt das strukturelle Transferrisiko nach Art. 44 ff. DSGVO nicht vollständig, schafft aber eine belastbare Compliance-Grundlage für viele Unternehmenseinsätze. Wer in regulierten Branchen (Gesundheit, Finanzen, öffentlicher Sektor) operiert, sollte die Rechtsabteilung einbeziehen. Für alle anderen ist das Risikoprofil vergleichbar mit anderen US-Cloud-Diensten, die mit SCCs arbeiten.

Die Weights-Provenienz ist transparent und unkompliziert: Apache-2.0-Lizenz, Entwickler klar dokumentiert, Weights öffentlich auf HuggingFace verfügbar. Wer das Modell lokal oder auf eigener Infrastruktur betreiben möchte, hat dazu das rechtliche Fundament.

## Fazit

gpt-oss:120b-cloud ist ein ernstzunehmendes Modell mit einem klaren Stärke-Schwäche-Profil. Die MoE-Architektur hält, was sie verspricht: Frontier-Qualität bei kompetitiver Geschwindigkeit, stabiler Cloud-Verfügbarkeit und einem Preis, der die meisten proprietären Alternativen deutlich unterbietet (0,0006 USD pro 1K Tokens, Benchmark-Gesamtkosten 0,0317 USD). Der Code-Quality-Score von 76,6% und der CLI-Score von 88,89% sind die überzeugendsten Einzelleistungen und machen das Modell zu einer ernsthaften Option für DevOps-Workflows, Security-Audits und technische Agenten-Pipelines.

Die Schwächen sind real, aber eingrenzbar. Das Reasoning-Modul leidet nicht an Denkfehlern, sondern an Kürze — wer das Modell mit einem höheren Reasoning-Budget betreibt (das Thinking-Optional-Feature ist dafür gemacht), dürfte hier andere Ergebnisse sehen. UX Writing und Cultural Intelligence zeigen eine Lücke im Bereich moderner deutscher Inklusivsprache, die für technische Anwendungsfälle irrelevant ist, für Kommunikations- und HR-Kontexte aber ins Gewicht fällt. Über alle Tests hinweg keine nennenswerten Halluzinationen — das Modell erfindet lieber nichts, als sich zu blamieren.

Das Gesamtbild: ein Modell, das für technische Produktivaufgaben bereit ist, ohne Einschränkungen kommerziell genutzt und feingetuned werden kann, und dessen Thinking-Optional-Architektur einen Hebel bietet, den viele Wettbewerber nicht haben. Wer es als Agenten-Backbone in einer DevOps-Pipeline einsetzt, wird wenig vermissen. Wer es für nuancierte sprachliche Aufgaben auf Deutsch einsetzt, sollte die Ausgaben gegenlesen.
